# Competition Control

Competition Control provides an OIDC-protected admin dashboard, PostgreSQL-backed competition data, match scheduling and live operations, scoring and standings, double-elimination playoffs, configurable public displays, and competition branding.

## Dashboard

The admin portal is grouped by what you are doing:

- **Event day** — *Overview* (what needs attention, each arena right now, coming up, leaders), *Live control* (one console per arena: the current or next match with a big clock and its controls, then the queue) and *Scores* (finished matches waiting for scores, entered inline, plus recent results and corrections).
- **Schedule** — *Schedule* (timeline, build, timed events, clear) and *Playoffs* (bracket diagram, seeding check, route to the final).
- **Setup** — Teams, Challenges, Arena colours, Displays. **Results** — League table. **Admin** — Competitions, Settings, Access & passkeys, Activity.

Everything updates live: the server pushes a change notification (Server-Sent Events) whenever data changes, and the dashboard, public displays and SR screens refresh immediately. Forms you are filling in are preserved across refreshes, and a refresh waits while you are typing. The sidebar shows how many matches are due to start and how many are waiting for scores. The layout works on phones (tables become cards, dialogs open as bottom sheets).

Running matches without entering scores is supported: when the timer ends the match shows END on the screens, then they move to the next match; the match waits in **Scores** and can be scored later or closed with **No score**. Matches that only lack scores never block clearing the schedule.

The left navigation separates Competitions, Overview, Teams, Challenges, Schedule, Live control, League table, Arena, Public displays, Settings and Activity. Playoff generation, scoring and scheduled heats are part of Schedule.

- Generate equal-appearance league schedules or add individual matches. Every match has four coloured positions; fewer than four teams requires a reason and is visibly marked.
- When generating a balanced schedule, **Start-to-start interval per arena** is the exact time between match start times in the same arena. A five-minute interval means consecutive starts are five minutes apart, regardless of match duration. The interval must be at least the configured match duration. Generated spacing is retained when schedule events or late starts cascade later matches.
- Set the competition's IANA timezone in Settings (for example, `Europe/London`). Schedule times in the admin portal, public schedule displays, and match history are rendered in that timezone; changing it affects displayed wall-clock times only, not stored match instants.
- Edit or delete pending matches after schedule creation. Deleting any non-running match requires typing its number and removes its saved scores/corrections while retaining an audit entry.
- Delay changes in Live control show the total time between the original scheduled start and current effective start, not the number of delay events. Upcoming matches can have their delay reduced, restored individually, or restored in bulk from **Future matches → Undelay all future matches**. Bulk restoration only resets unstarted league matches and active playoff heats whose original start is still in the future, skips countdowns and reports conflicts with active matches, other matches or events, and never moves an overdue match into the past. Reductions preserve the delay audit trail and are rejected if the earlier start would overlap another match or scheduled event.
- Start matches with a cancellable three-second countdown, delay starts, pause/resume timers, finish matches and enter/correct scores. Automatic/manual starts, explicit delays and timer resets only push later matches when the preceding match's expected end actually overlaps the next scheduled start; the configured gap is already represented by the next start and is not added a second time. If a match is reset before its existing scheduled/effective slot, that slot is preserved; otherwise it is moved to the next full minute. Live Control includes generated playoff heats alongside league matches: ready heats move into Active at their scheduled time, can be scored from the same score dialog, and scored heats remain in Past for corrections. Live Control labels matches with saved scores and offers score correction.
- Enable competition-wide auto-run in Live control to automatically start scheduled matches **and ready playoff heats** at their effective times. This is the only automatic-start setting; individual matches do not have start modes. If an automatic start is late, conflicting later matches and heats in that arena are pushed and recorded just like manual starts. A ready heat whose teams or arena are still busy waits until they are free, then gets a fresh synchronized countdown.
- A team or arena already occupied by a running or paused match cannot be started in another match. Manual starts, explicit delays, late automatic starts, resumes and timer resets push conflicting later matches in the same arena by whole-minute increments; updated effective times are immediately reflected in the schedule and public outputs.
- **Delay management.** Every delay, late start, resume, timer reset, schedule edit or event change runs one *re-flow* step: later league matches **and playoff heats in the same arena** keep their place in the queue and their planned spacing; playoff heats then follow the heats that feed them; finally everything moves around timed events. Running and paused matches hold their arena until their projected end. Nothing is ever pulled earlier automatically.
- Live control has a **Schedule status** strip showing, per arena, whether the next match or heat is on time, running behind (and by how much) or overdue to start.
- **Delay all upcoming…** (Live control → Future matches) moves every unstarted league match and playoff heat (optionally in one arena only) later by the same number of minutes with a reason. Spacing is kept, timed events such as lunch stay fixed, and anything that would now overlap them moves past them. Each league match gets a delay record; the action is audit logged.
- Playoff heats can be delayed and undelayed individually from Live control, like league matches. Undelaying a heat is refused if it would start before the heats that feed it have finished (plus its planned gap), or overlap another match or event in its arena.
- Arena diagrams use a square layout with team codes and the competition-wide position colours configured on the Arena page. Changing the four colours updates existing matches as well as future matches. Position 0 is bottom-left, then positions 1 (top-left), 2 (top-right) and 3 (bottom-right) clockwise.
- Create Timer, Arena or Corner public displays for live, server-synchronized clocks and starts. Timer, Arena and Corner displays take over the full screen for a shared two-second **GET READY**, three-second **3-2-1**, then **GO**. Countdowns always begin on a whole server second at least one second after Start is pressed (auto-run arms them two seconds early), so every screen already has the start time before GET READY appears. Every screen (admin, non-SR and SR) loads the same clock-sync script (`/assets/clock-sync.js`), which samples `/api/time` and keeps the lowest-latency estimate of the server offset, so all screens flip GET READY → 3 → 2 → 1 → GO on the same server second (measured within ~20 ms of each other on a LAN). The preparation/countdown background and alternate flash colour are configurable, as are the GO and END backgrounds. An optional final-seconds countdown (default 10 seconds, configurable from 1 to 60) appears before END. The END screen uses viewport-bounded text sizing so it fits narrow and short displays. Timer and Arena displays scale to fit the viewport without a page scrollbar (Arena gives more room to the arena, Timer to the clock); both can follow one arena and optionally show every team's score from the most recently completed, scored league or playoff match beneath the arena. The GO cue duration is configurable from one to five seconds. An optional END overlay can be shown for one to ten seconds when the match clock reaches zero. Corner displays ignore dark-theme configuration because their appearance is controlled by the chosen corner colour or the competition theme.
- The Public displays selector includes the original SR Arena, Outside, Producer, Shepherding and Staging pages from [SRComp Screens](https://github.com/srobo/srcomp-screens), rather than a visual re-creation. The original Polymer page/component markup and styles are served with the upstream MIT notice in `public/srcomp/LICENSE`; Competition Control supplies a read-only compatibility API and event stream backed by the selected competition. The standard SR schedule feed contains league matches only, while the knockout feed is explicitly selected for knockout views; Shepherding opts into both and keeps identically numbered matches distinct by bracket. The Outside display shows the schedule, leaderboard and available knockout brackets (not the league scores page); its schedule is ordered and displayed using effective slot start times so older matches with later numbers cannot appear after future matches. Arena and Producer can be pinned to an arena; Outside supports page visibility, rotation interval, leaderboard size, knockout round limit and an optional external competition link (none is shown unless configured); Staging supports a custom corner order. Their native full-screen layouts remain intact, with optional synchronized start/end cues and countdown colour settings applied to the original clock components. SR screens use the same shared server clock as every other screen; their one-second pulse is aligned to server-second boundaries and pushes changes to the screen immediately rather than waiting for Polymer's dirty-check. SR Arena and Producer show one arena: set it in the display options, or leave it blank to use the first arena. For best alignment, the server host must itself have a correct system clock (NTP); this synchronizes displays to the server, not the physical clocks on their devices to each other.
- Staging windows are computed on the server, so Shepherding, Staging and every other client agree. Set them per competition on the **Arena** page (Staging and shepherding): staging for a match opens when the previous match in its arena actually starts (or its scheduled start until then, and a configurable lead before the first match), and closes a configurable number of minutes later — never after the match itself starts. Times recalculate as matches start, are delayed or are rescheduled, and include playoff heats. Shepherding also has a recent-match history option (0–5, default one). Team codes on Shepherding are plain text coloured to match the competition-wide position colours configured on the Arena page; the board omits position headers and the arena heading for a single-arena event.
- SR screens are available to public displays only when the competition is published, live or complete. Their adapter exposes team standings, match positions and timing, scored matches, playoff brackets, configured arena colours, live delays and competition schedule events; it never exposes the authenticated admin endpoints. The live Arena/Producer match feed selects one active-or-next match per arena, includes starts initiated before their scheduled time, and ignores old awaiting-score matches so stale results cannot replace the match currently being shown. Shepherding status receives the complete schedule and evaluates the shepherd signal window against server-adjusted time. Since Competition Control records league points rather than separate game-score totals, the SR `game` score field represents accumulated match points and `league` represents total league points. SR screen assets and legacy Polymer/Web Components polyfills are vendored under `public/srcomp/` so the original HTML imports continue to work in current browsers; the Polymer dirty-check fallback remains active for background display tabs so live data continues to render without native `Object.observe`.
- The Public displays page lists configured displays first (Open, Configure, Copy URL/embed, Enable/Disable, Delete), warns when the competition is still a draft, and creates new displays with a type description and a URL slug suggested from the title. Create and Configure share one option list, and each display type only shows the options it actually uses (for example SR screens no longer show board-layout options they ignore). Each board display has its own dark-theme setting; schedule displays can independently hide completed events and completed matches.
- Correction reasons are shown and required only when replacing existing match scores; request failures remain visible until dismissed.
- Create challenges for the selected competition, award points once per team, and undo an award if it was entered in error. Both actions are recorded in the audit log.
- Add and edit custom timed schedule events such as lunch or talks. They appear chronologically alongside matches in the dashboard, public schedule JSON and schedule displays. Event time changes shift conflicting not-yet-started matches and later matches in the same arena by whole-minute increments; active matches and start countdowns are protected from being silently moved.
- Planned schedule reflow around events or arena conflicts updates match times without marking matches as operationally delayed. A currently running match takes priority over matches awaiting score on the live public Timer, Arena and Corner displays.
- To run a multi-day event, generate the league schedule from the first day's start time, then add break events to the Schedule before relying on the final times. For example, for a day beginning at 11:00 with a 13:30–15:30 break and a 17:00 finish, add a 120-minute event at 13:30 and an "Overnight break" event at 17:00 for 1,080 minutes (until 11:00 the next day). Matches overlapping either block, and later matches in the same arena, shift automatically. Choose the match count so the desired number of league matches fit before 17:00; any remaining matches roll into day two at/after 11:00. Add a lunch event on day two after the league matches, then generate the playoff bracket with its first heat scheduled after lunch. Upcoming, unscored playoff heats can be rescheduled individually from the Schedule table. Editing a heat's planned gap enforces the minimum interval before it; its start is moved later automatically if needed, while conflicting events are also respected. To add a 20-minute buffer before the final, edit the final heat and set its planned gap to 20 minutes (or more). If a previous match runs late, entering its result cascades later heats forward while retaining the planned gaps and shifting around events.
- Open the Competitions dashboard to create/select events or permanently delete one by typing its slug. Deletion removes its teams, matches, scores, challenges, brackets, settings and displays; an audit event is retained.
- Teams can be added to a competition at any time, including after publication and after matches have been scheduled. Newly added teams are not automatically inserted into existing matches; add or edit match assignments as needed. A team already assigned to a match cannot be deactivated, and teams with recorded history cannot be deleted.
- Competition standings total match points and challenge points. Each active team can receive a given challenge award once. Level teams are separated by match points, then head-to-head points (league matches where the tied teams met), then best single match. Teams still level are flagged ("level with … — judge to decide") on the league data, the Schedule page seeding banner and the seeding sanity check, rather than silently ordered by team code.
- **Playoff ties are the judge's call.** When teams finish a heat on equal points and their places lead to different outcomes (one advances and one drops or is eliminated, or any placing in the final), the score cannot be saved until the judge chooses the order and records a reason, for example after a replay. Ties that don't change anything (e.g. 3rd and 4th both dropping to the same lower-bracket heat) save normally. The decision is stored with the heat, shown on its bracket card and audit logged. Heat results everywhere follow the stored placings.
- **Playoffs after the league.** On the Schedule page choose the route to the final (see [docs/operations-guide.md](docs/operations-guide.md#playoffs) for worked examples):
  - **Double elimination** — finish below a heat's advancing places once and you drop to the lower bracket; a second loss eliminates you. The final brings together upper- and lower-bracket survivors.
  - **Single elimination knockout** — finish below the advancing places in any heat and you are out.
  - **Straight to the final** — the top 2–4 league teams play one final heat.
  - **Teams in the final** — 4 (default), 3, or 2 for a head-to-head final.
  - **Top seeds straight to the final** — the league winner (or top 2/3 seeds) skip the knockout rounds; the remaining final places are earned. Double elimination needs at least two earned places.
- Any field from 2 teams up to every active team works. Heats have two to four robots; a round never leaves a single team with a bye (a remainder of one becomes a 3-team and a 2-team heat). First-round heats are seeded in a serpentine so the top seeds are spread out, and later rounds avoid putting two teams from the same previous heat together where heat sizes allow. Top two progress from 3- and 4-team heats, the winner from a 2-team heat; where a round has to finish with an exact number of finalists, the heat card states how many progress. The form shows a live preview of the heat count, stages and who reaches the final before anything is generated.
- Set the first heat's start, the arenas (comma-separated), the minutes between heats, and an optional extra delay before the final. With several arenas, heats that do not depend on each other run side by side; a heat never starts before the heats feeding it have finished and been scored, plus the gap. Heats are scheduled after the existing schedule by default and moved around timed events. Moves made while first placing the bracket count as its plan, not as delays.
- The **Playoff bracket** card on the Schedule page draws the bracket as a diagram: one box per heat in stage columns (upper/knockout bracket on top, lower bracket below, final on the right) with a line from each heat to the entrant slot it fills — solid for the winners' path, dashed where teams drop to the lower bracket, green into the final. Boxes show time, arena, entrants (or where they will come from, e.g. "2nd · heat 9") and, once scored, placings with points (advancing places highlighted). The same diagram appears in the generation form preview before anything is created, and on the public Playoff bracket display. Heat cards and a team progress table (losses, still in / eliminated) are underneath.
- Playoff heats have separate schedule records and score storage, use the same score-entry dialog and synchronized timer controls, shift around regular matches and timed events, and never add their scores to league points. Heats in an arena run in schedule order: a heat still waiting for earlier results holds up the heats after it (Live control shows it as next, auto-run waits, and starting a later heat is refused until the earlier one is played or delayed past it). In Live Control, an assigned ready heat can be started before its scheduled time with **Start now**; its three-second countdown starts the timer, moves dependent heats forward while retaining their planned gaps, and checks that its arena and teams are not already active. Pause, resume or finish it from the same controls, then enter scores when it is awaiting score. An unscored running, paused, or finished heat can be reset from Live Control; this clears its timer and schedules it for the next full minute, moving later heats as needed. Reset is blocked after scores are saved. Timer, arena, and corner displays follow the active playoff heat as well as league matches. Correcting a heat requires a reason and is blocked when a dependent heat already has scores. Replacing a bracket archives its previous progression.
- Upcoming playoff heats can be edited from Schedule to change their time, arena, or planned gap while retaining dynamic team assignment. Completed or scored heats cannot be rescheduled. Deleting league matches is available in Schedule only, not Live control.
- Create public league, schedule, match points history, **playoff bracket**, arena, timer and corner displays. Schedule displays show league and playoff heats plus timed events in chronological order, with four position columns coloured to match arena corners and an optional team dropdown filter. Delayed matches show the original time struck through next to the new time and a "Delayed N min" status, the live and next rows are highlighted, and a banner says how far behind schedule the event is running. Playoff bracket displays lay the heats out by stage with results and eliminated teams. Board-style displays refresh in place every five seconds (no page flash, the team filter is kept) and show "Connection lost" if the server cannot be reached. Schedule times use the competition's configured IANA timezone, including daylight-saving changes, rather than the server's timezone. Corner displays make the selected team's three-letter code primary, with options for a full-screen corner colour, a large background position number and the team name. The live clock labels upcoming starts as “STARTS IN” and running/paused match time as “TIME LEFT”. Each display provides an HTML URL and a JSON endpoint and can be embedded with an iframe.
- Schedule displays can replace clock times with a live-updating relative time (“in …” / “… ago”), hide the arena column (Show arena name) and follow one arena. Live screens never show “awaiting score”: a finished match stays only while its END cue shows, then the next match’s “starts in” or “waiting to start” takes over. A Match points history display lists every completed league and playoff match and the exact points scored by each team in its arena position; playoff scores remain separate from league standings.
- Live control separates matches into Active, Future matches (soonest first) and Past matches (most recent first). State changes move a match immediately to its new section without duplicating it. The four arena positions are shown as compact colour-dot/code labels instead of a large arena diagram.
- From the Schedule page, choose **Clear matches only** to remove league matches, playoff heats/brackets, scores and correction history while retaining custom timed events, teams, challenges, settings and displays. Choose **Clear all scheduled content** to also remove custom timed events. Both actions require two UI confirmations, are blocked while any league or playoff match is running, paused, awaiting score or in its start countdown, and are audit logged.
- Choose the Paper, Field or Night theme and upload a PNG, JPEG or WebP logo up to 1 MiB.
- Save one distinct colour for each of the four arena positions in Arena settings; the server applies the palette to all match position records and all newly created/generated matches.
- The admin portal works on phones: tables turn into one card per match with labelled fields and full-width action buttons (Start, Delay, Score are always visible), the header shrinks to a scrollable menu plus the competition picker, and dialogs open as bottom sheets. Public schedule displays fit all four team columns on a phone by folding the arena under the match number and the status under the time.
- Dashboard data updates automatically while the page is open. Unsubmitted form edits are preserved while updates arrive; the sidebar stays fixed while the main content scrolls.
- Schedule position cells use only the colour-coded team code; the numbered positions remain in the column headings. Arena diagrams show the large position number in each cell's corner and make the synchronized "starts in" countdown prominent.

## Deployment

Docker and Docker Compose are required. The app listens on port 8080 inside the container; Compose publishes it on all host interfaces. The app does not terminate TLS. Use a TLS reverse proxy for public access and OIDC callback traffic.

1. Create `.env` using `.env.example`.
2. Set a unique `POSTGRES_PASSWORD`, a random `COOKIE_SECRET` of at least 32 characters, `PUBLIC_BASE_URL`, and the OIDC issuer, client ID, client secret and callback URI.
3. Configure the identity provider for OIDC Authorization Code with PKCE, the `openid`, `profile` and `email` scopes, and callback `${PUBLIC_BASE_URL}/auth/callback`.
4. Start the service with `docker compose up -d --build`.
5. Check `curl http://127.0.0.1:8080/health`, then sign in through the public HTTPS URL.

Sessions use HttpOnly, SameSite=Lax cookies; use `COOKIE_SECURE=true` behind HTTPS. For local-only development, use `COOKIE_SECURE=false` and do not expose the service publicly.

## Sign-in and security

- **Organisation sign-in (OIDC)** is the normal way in. The account's email identifies the administrator (falling back to the username). Set `ADMIN_EMAILS` (comma-separated) to restrict sign-in to named people; leave it empty to allow any account the identity provider accepts. Every allowed administrator has full access. If your identity provider lets people register themselves, also set `OIDC_REQUIRE_VERIFIED_EMAIL=true` so only emails the provider has verified are accepted (it is off by default because Authentik's standard email mapping reports every email as unverified).
- **Passkeys are the fallback, and the only one** (there are no passwords). Each administrator can add passkeys under **Admin → Access & passkeys**; they then sign in with their device's fingerprint, face or PIN even when the identity provider is down. Passkeys require HTTPS at `PUBLIC_BASE_URL` (they are bound to that host name) and always require user verification.
- **If the identity provider is down when the app starts**, the app still starts; passkey sign-in works and discovery retries in the background.
- **Break-glass enrollment**: someone with shell access on the server can create a one-time passkey link (valid 30 minutes by default) for an administrator who has no passkey yet:
  ```sh
  docker compose exec app node dist/cli.js invite person@example.com
  docker compose exec app node dist/cli.js users
  ```
- **Accounts** appear under Access & passkeys after their first sign-in. Disabling one signs it out everywhere and blocks its passkeys; you cannot disable yourself. "Sign out everywhere" ends all other sessions.
- **Protections**: state-changing requests must come from this site (Origin check) on top of SameSite cookies; the admin pages cannot be framed; sign-in endpoints are rate limited per client (configure `TRUST_PROXY` to match your reverse proxy so client addresses are correct); sessions last 12 hours; sign-in and passkey changes are audit logged.

## Public outputs

Create outputs in the dashboard's Public displays page. An enabled display is available at:

- HTML: `/display/{display-slug}`
- JSON: `/api/public/display/{display-slug}`

League standings also have fixed compatibility routes:

- JSON: `/public/v1/{competition-slug}/league`
- Iframe: `/embed/{competition-slug}/league`
- Schedule JSON: `/public/v1/{competition-slug}/schedule` (`matches`, `events`, and chronologically sorted `items` arrays)
- Live timer JSON: `/public/v1/{competition-slug}/timer` (current match, position/colour assignments and timer state)

Displays are read-only and are available after the competition is published. Disable or delete displays from the admin page. Editing a display's settings updates every open copy of it within a second (the screen reloads itself), so screens can be reconfigured remotely. Open screens also reload once after the server restarts, so they pick up new display code after a deploy.

### Custom screens, knockout diagram and sound

- **Knockout diagram** shows only the playoff bracket diagram, scaled to fill the screen.
- **Custom screen** lays out panels in a full-screen, side-by-side, main-and-sidebar or four-quarter layout. Each area shows one or more panels — schedule, league table, knockout diagram, latest scores, live match timer, an announcement you type in, or rotating sponsor images — and rotates between them. Rotation is timed from the server clock, so copies of the same screen change together. Panels are the standard displays rendered inside the custom screen (`/display/{slug}/panel/{kind}`), sharing one change-feed connection.
- **Race beeps** (Timer, Arena, Corner and custom screens): short beeps on 3, 2, 1, a long high beep on GO and a horn at the end, scheduled on the browser's audio clock against server time (measured within ~6 ms of each server second).
- **Audio & media** (Event day) uploads tracks (MP3, M4A, AAC, OGG, WAV, FLAC, up to 50 MB each) and images (PNG, JPEG, WebP, GIF), 2 GB per competition, stored in PostgreSQL and served with byte ranges from `/media/{id}` once the competition is published. Tick **Play the competition audio** on the screens wired to speakers. The playlist is synchronised without streaming: the server stores when the playlist started and every screen works out the same track and position from its server clock, correcting drift by nudging playback speed (screens measured within a few milliseconds of each other).
- **Live audio** sends a sound source from the admin browser — a line-in or microphone, or a shared browser tab (for example a music service playing in a tab) — to every audio screen, on any network. The admin browser encodes it as Opus (WebCodecs) in 20 ms chunks stamped with their capture time on the server clock and posts them a few times a second; the server relays them to the screens over their event stream (ordinary HTTPS, so it works through Cloudflare). Each screen decodes the chunks and plays every one exactly one second after it was captured, so all screens play the same sound at the same moment. Keep the broadcasting page open; closing it ends the broadcast after 15 seconds. Broadcasting and listening need a current Chrome or Edge. For a TV, soundbar or Bluetooth speaker that adds its own lag, set **Speaker delay** on that display; the screen then plays that much earlier (this applies to the playlist too). Spotify itself cannot be played on several devices at once, so play it on the broadcasting computer and share that tab or its sound output.
- Browsers only play sound after a click on the page; screens show **Click to enable sound** until then. For unattended kiosks start the browser with `--autoplay-policy=no-user-gesture-required`.

## Development and validation

```sh
npm test                 # unit tests (pure scheduling, playoff, display logic)
npm run typecheck
npm run build
npm audit --omit=dev
# integration tests against a real PostgreSQL (see docs/REPOSITORY.md)
TEST_DATABASE_URL=postgres://... npm run test:integration
```

`npm test` covers the pure scheduling, playoff, display and SR adapter logic, including every playoff format × final size × bye combination for fields of 2–40 teams. `npm run test:integration` boots the whole app against a real PostgreSQL and runs: a fuzzer that sends 8,000+ hostile requests to every route and fails on any server error; auth tests (sessions, allowlist, disabled users, cross-site requests, framing, rate limits); complete passkey registration and sign-in with a software authenticator (including tampered, replayed and wrong-site credentials); live-match lifecycle and concurrency tests; and randomised schedule tests that apply hundreds of operations and check after each that no two matches overlap, nothing runs during an event, and playoff heats follow their feeders. See [docs/REPOSITORY.md](docs/REPOSITORY.md#local-end-to-end-testing).

Schema setup runs when the server starts (new columns are added with `ADD COLUMN IF NOT EXISTS`, so upgrading an existing database is automatic). Back up the `postgres_data` volume and verify a restore before event use. Versioned schema migrations and automated browser integration coverage are release-readiness work.
